# ChangeFence

**Security change control for AI agents.**

> Your code diff is not your agent diff.

[![CI](https://github.com/karteekponnuru/ChangeFence/actions/workflows/ci.yml/badge.svg)](https://github.com/karteekponnuru/ChangeFence/actions/workflows/ci.yml)
[![License](https://img.shields.io/badge/license-MIT-555.svg)](LICENSE)

ChangeFence detects security regressions when an AI agent changes models, prompts, tools, permissions, or delegation relationships.

A normal code review can show that a tool was added or a prompt changed. It does not always make the resulting **security capability** obvious. ChangeFence compares a trusted baseline with a candidate release and asks:

1. What security-relevant authority became newly reachable?
2. Did adversarial behavior become worse in the candidate release?
3. Does the release violate a security invariant that should block deployment?

## Why this exists

Consider two agents:

```text
Procurement Agent                  Finance Agent
- supplier.read                    - invoice.read
- supplier.write                   - payment.execute
```

Both configurations can be individually valid.

A release adds one delegation relationship:

```text
Procurement Agent  ──delegates──>  Finance Agent
```

The resulting authority graph now contains:

```text
procurement
    ↓
delegate:finance
    ↓
finance
    ↓
tool:payments
    ↓
payment.execute
```

If the policy states that Procurement must never gain authority to execute payments, ChangeFence identifies the newly reachable path and fails the release gate.

```text
CHANGEFENCE

Baseline   main
Candidate  release/284

Security gate  FAIL

[CRITICAL] FIN-001
Procurement must never gain authority to execute payments.

New authority path
procurement → finance → payment.execute

Suggested action  BLOCK RELEASE
```

## What ChangeFence does

### 1. Authority security diff

ChangeFence models:

- agents
- tools
- capabilities
- agent-to-agent delegation
- models and prompts
- capability severity
- security invariants

It computes transitive reachability for both baseline and candidate systems, then reports only security-relevant paths introduced by the candidate release.

### 2. Behavioral security diff

ChangeFence can compare repeated adversarial test outcomes generated by any agent framework.

Example:

```text
Scenario                         Baseline   Candidate   Result
indirect_prompt_injection        100%       30%         REGRESSION
data_exfiltration                90%        90%         UNCHANGED
tool_authority_escalation        100%       40%         REGRESSION
```

The agent framework is responsible for executing scenarios. ChangeFence is responsible for comparing releases and applying the security gate.

### 3. Local AI red-team hypotheses

ChangeFence can optionally use a **local LLM through Ollama** to propose attack hypotheses without sending the agent architecture to a hosted model.

The model is the explorer, not the judge:

```text
Local LLM
   ↓ proposes attack hypotheses
ChangeFence deterministic verifier
   ├─ VERIFIED_NEW
   ├─ VERIFIED_EXISTING
   └─ UNREACHABLE
```

If the model invents a path that the candidate cannot actually reach, ChangeFence rejects it as `UNREACHABLE`. The model never decides whether the release gate passes.

Run the local hypothesis engine:

```bash
changefence hypothesize \
  examples/procurement-base.yaml \
  examples/procurement-candidate.yaml \
  --model gemma3
```

See [`docs/local-llm.md`](docs/local-llm.md) for the design and setup.

### 4. Deterministic release gate

Security invariants are evaluated outside the LLM.

An LLM may help generate attack hypotheses, but it does not decide whether a capability path exists or whether a policy has been violated.

That distinction is intentional.

## Quick start

Requires Python 3.10+.

```bash
python -m pip install -e .
```

Compare two agent-system definitions:

```bash
changefence compare \
  examples/procurement-base.yaml \
  examples/procurement-candidate.yaml
```

Compare repeated behavioral-test results:

```bash
changefence behavior-diff \
  examples/behavior-base.json \
  examples/behavior-candidate.json
```

Generate a standalone HTML report:

```bash
changefence report \
  examples/procurement-base.yaml \
  examples/procurement-candidate.yaml \
  --behavior-base examples/behavior-base.json \
  --behavior-candidate examples/behavior-candidate.json \
  --out changefence-report.html
```

A security regression exits with a non-zero status code so the check can block CI/CD.

## GitHub Action

ChangeFence can be used as a release gate inside another repository:

```yaml
- name: ChangeFence agent security gate
  uses: karteekponnuru/ChangeFence@main
  with:
    baseline: security/agent-baseline.yaml
    candidate: security/agent-candidate.yaml
    fail-on: high
```

## Agent system format

The developer integration uses YAML as a compact machine-readable description of agents and their authority. The browser demo does not require users to understand YAML.

```yaml
system: acme-procurement

agents:
  procurement:
    tools: [supplier]
    delegates_to: [finance]
  finance:
    tools: [payments]

tools:
  supplier:
    capabilities:
      - name: supplier.bank_account.write
        severity: high
  payments:
    capabilities:
      - name: payment.execute
        severity: critical

invariants:
  - id: FIN-001
    severity: critical
    description: Procurement must never gain authority to execute payments.
    forbid_reachability:
      from: procurement
      to: payment.execute
```

## Architecture

```text
Local LLM ───────> attack hypotheses ───────┐
                                            ↓
Baseline system ─┐                    deterministic
                 ├─> capability graph ─> verification ─┐
Candidate system ┘                                     │
                                                       ├─> security gate
Behavior baseline ─┐                                   │
                   ├─> behavioral regression diff ─────┘
Behavior candidate ┘
```

## Current scope

ChangeFence is a release-time security analysis layer. It does not replace IAM, runtime authorization, model safety filters, monitoring, or human approvals.

The current focus is narrower: detect when an agent release creates security behavior or authority that did not exist in the known-good baseline.
